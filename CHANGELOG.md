- Fix CI: `.github/workflows/ci.yml`'s backend job started Postgres and waited for connectivity, but never ran `alembic upgrade head` before `pytest` — so every test hitting `leads`/`lead_resumes` failed with `relation "..." does not exist` on a genuinely fresh database (GitHub Actions runners always start empty; this never showed up locally because the local `.pg0data/` had already been migrated once and just kept accumulating state). Added the missing `alembic upgrade head` step. Reproduced and verified the fix locally against a fresh throwaway Postgres instance before pushing.
- Implement lead-created email notifications: `app/services/notifications.py::notify_lead_created()` now actually sends (prospect confirmation + attorney alert) via plain SMTP (`smtplib`, stdlib), configured through new `Settings` fields (`smtp_host`/`smtp_port`/`smtp_use_tls`/`smtp_username`/`smtp_password`/`smtp_from_address`/`attorney_email`) and documented in `backend/.env.example`. No-ops (logged) if SMTP isn't configured, so the app still runs without it. Chosen over a real email API (Resend/SES/etc.) or a local catcher (Mailpit) specifically because plain SMTP can send to *any* address — needed since the attorney recipient can be an arbitrary/fake address, which a sandboxed free-tier API would reject. Found and fixed a real bug while verifying against a genuine (if local) SMTP server: unconditionally calling `server.login()` breaks against any server that doesn't support SMTP AUTH (real Gmail requires it; a plain local dev server doesn't); fixed by checking `server.has_extn("auth")` first. Added `backend/tests/test_notifications.py` (mocked SMTP, no real network calls).
- Fix a real risk: once real SMTP credentials exist in `backend/.env` for actual app usage, `pytest` would have picked them up too — `get_settings()` loads `.env` for both. Added an autouse fixture in `backend/tests/conftest.py` that forces `SMTP_USERNAME`/`SMTP_PASSWORD` empty for every test regardless of local `.env` contents, so filling in real credentials for the running app can never cause the test suite to send real email. Documented in `SECURITY.md`.
- Rewrite the notification email content: proper subject lines, warmer prospect copy, and an attorney email that includes the resume filename, formatted submission time, and a direct "View lead" link/button to `/internal/leads` (new `Settings.frontend_base_url`). Both emails are now `multipart/alternative` (plain text + styled HTML), not plain-text-only — partly for quality, partly because plain-text-only script mail is flagged as spam more aggressively, which is what caused the attorney notification to go missing in testing (Gmail fully accepted both messages at the SMTP level; the difference was downstream spam filtering, not a bug). Strengthened `test_notifications.py` to assert on actual email content (both text and HTML parts), not just headers.
- Add attorney auth — the last of the three required pieces. Backend: `attorneys`/`attorney_sessions` tables (PBKDF2-HMAC-SHA256 password hashing via stdlib `hashlib`, no new dependency; opaque bearer tokens with server-side expiry/revocation), `POST/GET /api/v1/auth/{login,logout,me}`, and `CurrentAttorney`/`app.api.deps` now gate `GET /api/v1/leads`, `POST /api/v1/leads/{id}/reach-out`, and `GET /api/v1/leads/{id}/resume` (lead creation stays public, per spec). The first migration seeds a dummy `admin`/`admin` account (via the real `hash_password()`, not a hardcoded hash) so the app works out of the box; `backend/scripts/create_attorney.py` adds real accounts later. Frontend: `/login` page + Server Action sets an httpOnly session cookie; `internal/layout.tsx` is now a real auth guard (validates against `/api/v1/auth/me`, redirects to `/login` if invalid, shows a "Signed in as {username}" header with logout); every authenticated backend call happens server-side (Server Components/Actions) rather than from the browser, and resume downloads go through a new Route Handler proxy (`internal/leads/[id]/resume/route.ts`) since the httpOnly cookie isn't readable by a plain `<a href>`. Updated `backend/tests/test_leads.py` (added `401`-without-auth cases, auth headers via a new `auth_headers` fixture) and added `backend/tests/test_auth.py`. Verified end-to-end with a real browser: unauthenticated redirect, wrong-password error, successful login, protected page rendering, resume download through the proxy, the reach-out action, logout, and confirming logout actually invalidates the session server-side (not just client-side).
- Fix two real bugs hit while verifying the above: (1) `uvicorn --reload`'s file-watcher intermittently served stale routes on this machine even across restarts — worked around by running without `--reload` when in doubt; (2) separately, port 8010 developed a genuinely stuck OS-level socket (a `LISTENING` entry with no owning process), which was masking bug (1)'s fix and causing new server instances to silently fail to bind. Backend/frontend are running on port 8012 for this session as a workaround (see `DECISIONS.md` known limitations) — 8010 remains the documented default and should work again after this machine reboots.
- Fix a real gap: the seeded `admin`/`admin` account was created unconditionally by `alembic upgrade head`, including against a hypothetical production database. Added `Settings.seed_dev_admin` (env var `SEED_DEV_ADMIN`, default `false`) and gated the migration's seed insert behind it; set to `true` in `backend/.env.example` (local dev) and `.github/workflows/ci.yml`'s migration step (CI needs it — it migrates a fresh DB every run and the auth tests depend on the seeded account). Verified against three separate fresh throwaway Postgres instances: unset/false → zero attorneys created; explicitly `true` → the account exists, exactly as expected.

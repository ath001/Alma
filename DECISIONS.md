# Decisions

A topical reference for *why* the codebase looks the way it does — key decisions, the tradeoffs behind them, and real bugs hit along the way. [CONVERSATION_LOG.md](CONVERSATION_LOG.md) is the chronological session-by-session record; this file is the distilled, organized version for someone trying to understand the current shape of things without reading the whole history.

## Local dev environment

- **Postgres via [pg0-embedded](https://pypi.org/project/pg0-embedded/)**, not Docker/SQLite/a native install. No DB was found on the machine at all (checked services, listening ports, Program Files, Docker, CLI tools). Chosen because it gives a *real* Postgres — same dialect/behavior as production — with zero setup (no installer, no Docker Desktop). `pgserver` was the first candidate but has no Windows distribution; `pg0-embedded` does. SQLite was rejected as the primary local DB because dialect differences can mask real bugs. `scripts/run_db.py` / `scripts/stop_db.py` wrap it; data lives in gitignored `.pg0data/`.
- **Backend default port is 8010, not 8000.** This dev machine already had something else (ComfyUI) bound to 8000; rather than just documenting a workaround, 8010 was made the permanent default everywhere so the conflict doesn't recur on other machines either.
- **Node.js wasn't installed at all** — installed via `winget install OpenJS.NodeJS.LTS` with explicit user approval before scaffolding the frontend.

## Repo structure

- **Monorepo**: top-level `backend/` (FastAPI) and `frontend/` (Next.js), each self-contained with its own dependency manifest and README, plus shared root-level dev tooling (the DB scripts). Chosen over two separate repos — simplest for a project this size; independent deploy/versioning wasn't a stated requirement.
- **Backend deps via `pyproject.toml`**, not `requirements.txt` — one file for both dependencies and tool config (ruff, pytest), the modern default for production FastAPI repos.
- **Frontend scaffolded with Tailwind** (`create-next-app --tailwind`) — fast to style the form/list, no reason to avoid it.
- **`docker-compose.yml` deferred**, not built yet — `project.txt` doesn't require Docker, and pg0-embedded already solves "no install needed" for local dev. Revisit when there's an actual deploy target.
- **`Requirements.txt` renamed to `project.txt`** — despite the name it was never a pip file, it's the product/tech assignment; the old name was actively misleading.

## Backend architecture

- **`/api/v1` prefix from the start** — avoids a URL restructure if there's ever a breaking v2.
- **DB access via a `DbSession = Annotated[Session, Depends(get_db)]` alias**, centralized in `app/api/deps.py`. (This pattern was actually started by the user/their IDE mid-session in `health.py`; adopted and centralized rather than reverting.) Never a module-level session or an inline `Depends()` default.
- **Explicit CORS allow-list** from `Settings.cors_origins` (default `http://localhost:3000`), not `allow_origins=["*"]`.
- **Alembic wired up from day one**, even before any real migration existed — establishes the autogenerate → review → upgrade pattern before there's anything real to migrate.
- **Backend tests run against the real local Postgres**, not SQLite or mocks — matches production dialect/behavior. Tradeoff: there's no per-test transaction-rollback fixture, so test runs leave real rows behind in the shared local DB (see Known limitations below).

## Lead feature design

- **Lead ID: UUID, not auto-increment int.** `POST /leads` is public and unauthenticated — sequential IDs would let anyone infer submission volume over time and made `/leads/{id}/resume` guessable for other prospects' files. UUID closes both at negligible cost.
- **State: SQLAlchemy `Enum(..., native_enum=False)`** (VARCHAR + CHECK), not a native Postgres enum type. Only two values today (`PENDING`, `REACHED_OUT`), but a future third state is realistic; a native PG enum needs `ALTER TYPE` surgery to extend, this just needs a constraint change.
- **Resume storage: kept in Postgres** (`lead_resumes` blob table, `bytea`), *not* the filesystem. The initial plan proposed local-filesystem storage (mirroring the "real, zero-setup, local-first" philosophy already used for the DB itself), but the user redirected: no second storage system to stand up for a dev-stage app when Postgres is already the only infra, and it's transactional — the blob and the `Lead` row commit together, so a crash mid-request can't orphan a file the way a filesystem write + separate DB commit could. Kept swappable: a `StorageBackend` Protocol (`app/services/storage.py`) plus a `resume_storage_backend` setting (`"postgres"` today, `"s3"` reserved and stubbed to raise `NotImplementedError`) — moving to S3 later is one class + a setting flip, not a rewrite of call sites.
- **Resume download via a dedicated `GET /leads/{id}/resume` endpoint**, not a static file mount. A mount can't validate the lead exists, can't set correct `Content-Type`/`Content-Disposition`, and can't be auth-gated later without changing the URL contract — the dynamic endpoint can do all three, and the URL shape stays stable even after swapping storage backends.
- **State transition via a dedicated `POST /leads/{id}/reach-out` action endpoint**, not a generic `PATCH /leads/{id}`. The only valid transition is one-directional and attorney-triggered; a generic PATCH would imply arbitrary field edits (renaming a prospect, changing their email) nothing asked for. `409 Conflict` if the lead isn't currently `PENDING`.
- **`resume_storage_key` is a plain string column, not a DB foreign key** — deliberately, so the column doesn't hardcode assumptions about which storage backend produced it (an S3 object key isn't a Postgres FK target).
- **Email via plain SMTP (`smtplib`, stdlib) against the user's own Gmail account with an App Password**, not a real email API (SES, Resend, SendGrid, etc.) and not a local SMTP catcher (Mailpit). The user specifically wanted the prospect's email to genuinely be deliverable while the attorney address could be an arbitrary/fake one — a free-tier API like Resend restricts sending to *verified* addresses only in sandbox mode, which would have blocked an arbitrary fake attorney address; plain SMTP has no such restriction, sends to any address, and needs no new account or dependency (`smtplib`/`email` are stdlib). `notify_lead_created()` no-ops (logged) if `SMTP_USERNAME`/`SMTP_PASSWORD` aren't set, so the app runs fine without email configured — same "optional, graceful, real-when-configured" shape as the rest of this build.

## Auth design

- **Real `attorneys`/`attorney_sessions` tables in Postgres**, not a hardcoded `admin`/`admin` check in code. The user explicitly wanted the dummy account to "function like just an attorney that can be added later with his own credentials" — a hardcoded check couldn't satisfy that; a real user table (seeded with one row) can, and `backend/scripts/create_attorney.py` is the extension point.
- **PBKDF2-HMAC-SHA256 (stdlib `hashlib`), not bcrypt/`passlib`.** Keeps the pattern established throughout this build (prefer stdlib over a new dependency when it's genuinely adequate) — 200k iterations is a reasonable modern default and this isn't a high-value target (assignment-stage, one seeded dummy account).
- **Opaque bearer tokens stored in Postgres (`attorney_sessions`), not JWTs.** Same "keep state in Postgres, one piece of infra" philosophy as resume storage. A DB-backed session can be genuinely revoked (`DELETE`, which `POST /auth/logout` does) — a JWT can't be un-issued before it expires without adding a denylist, which is the same DB-table mechanism anyway, just for the negative case instead of the positive one.
- **The seed account is created inside the Alembic migration itself** (calling the real `hash_password()`, not a hardcoded hash blob), not a separate "run this after migrating" step — so `alembic upgrade head` alone leaves the app fully usable, matching this project's "minimal setup" thread throughout (pg0-embedded, no Docker, etc.).
- **The seed is gated behind `SEED_DEV_ADMIN` (off by default), not unconditional.** Initially it ran on every `alembic upgrade head`, on any database, including a hypothetical production one — the user asked directly whether `admin`/`admin` would "always" be created, which surfaced that this was a real gap, not just a documentation caveat. Chosen over environment-name sniffing (e.g. "skip if `ENV=production`") because an explicit opt-in setting is safer by construction: a new environment defaults to *not* getting the account unless someone deliberately flips it on, rather than defaulting to getting it unless someone remembers to name the environment correctly. Set to `true` in `.env.example` (local dev) and in `.github/workflows/ci.yml`'s `alembic upgrade head` step (CI migrates a fresh DB every run, and `test_auth.py`/the `auth_headers` fixture depend on the seeded account existing) — both deliberately, not by the same "off" default.
- **Token transport: httpOnly cookie set by a Next.js Server Action, forwarded to the backend as `Authorization: Bearer` only by Next.js's own server code** — never a cookie the backend itself sets or the browser sends directly to the backend. This was a deliberate choice over letting the backend set the cookie directly: frontend (`localhost:3000`) and backend (`localhost:8010`) are different origins, and while browsers happen to scope cookies by hostname (not port) — meaning a cookie set by the backend at `localhost:8010` would actually be sent by the browser to `localhost:3000` too, a quirk that makes local dev deceptively easy — that behavior is `localhost`-specific and wouldn't hold once frontend/backend are on genuinely different real domains in production. Routing the token exclusively through Next.js's own server avoids relying on that quirk at all, at the cost of needing a small Route Handler (`internal/leads/[id]/resume/route.ts`) to proxy resume downloads, since a plain `<a href>` straight to the backend can't carry an httpOnly cookie the browser can't read.

## Scope boundaries (deliberate, not oversights)

Each of these has a TODO/seam in the code rather than being silently missing:
- **Auth for `/internal` and the corresponding backend endpoints** (`GET /leads`, `POST /leads/{id}/reach-out`) — both currently unauthenticated. Mechanism not chosen yet (NextAuth vs. backend-issued session vs. something else).
- **"Mark reached out" UI** — done: a Server Action (`internal/leads/actions.ts`) posts to `POST /api/v1/leads/{id}/reach-out` and `revalidatePath`s the page. Chosen over a client component with `fetch`+`useState` because a plain `<form action={...}>` needs zero client-side JS or loading state — Next.js handles the round trip and re-render itself, and it degrades gracefully (still a real HTML form submission under the hood).

## Debugging log

Real bugs found and fixed during this build (not exhaustive — see [CONVERSATION_LOG.md](CONVERSATION_LOG.md) for the full narrative):

- **Orphaned `postgres.exe` processes.** `run_db.py` only called `pg.stop()` on a clean `KeyboardInterrupt`; a forceful termination (SIGTERM) skipped the `finally` block entirely, leaving Postgres running in the background. Fixed with a `SIGTERM` handler that converts to `SystemExit` so cleanup always runs; `stop_db.py` added as a manual fallback for anything already orphaned.
- **Alembic autogenerate silently produces empty migrations for unregistered models.** `alembic/env.py` imported `app.models.base` (for `Base`), not `app.models` as a package — so a new model that's never imported anywhere never registers on `Base.metadata`, and autogenerate sees nothing. Fixed by importing every model in `app/models/__init__.py` and having `env.py` pull `Base` through that package import. **Convention going forward: any new model must be added to `app/models/__init__.py`.**
- **A running backend can silently serve stale code.** Restarted the server without `--reload` at one point; new endpoints returned `404` despite existing on disk, because the running process was importing the old module. Caught by checking the process's actual command line before assuming the code was broken.
- **No per-test DB isolation.** Backend tests hit the real local Postgres directly with no transaction-rollback fixture, so every `pytest` run leaves real rows behind. Not a correctness bug in the app, but required manually `TRUNCATE`-ing `leads`/`lead_resumes` several times during this session to hand back a clean DB. Flagged as a known limitation — see below.
- **Unconditional `server.login()` breaks against a no-auth SMTP server.** First draft of `notify_lead_created()` always called `smtplib`'s `login()`. Verified the whole flow against a real (if local) SMTP server before trusting it — installed `aiosmtpd` temporarily, ran a debug SMTP server with no AUTH support, and got `SMTPNotSupportedError: SMTP AUTH extension not supported by server`. Real Gmail requires login; a plain dev/local catcher (this one, and Mailpit too) doesn't support AUTH at all. Fixed by checking `server.has_extn("auth")` before calling `login()`, so the same code works unmodified against both. (Separately: the debug server's own console/log output mangled a non-ASCII em dash on this Windows machine — confirmed via raw-byte inspection that our code emits correct UTF-8 on the wire; that corruption was the debug tool's own print pipeline, not our bug.)
- **Public form's submit button did nothing.** `handleSubmit` was a deliberate stub (`e.preventDefault()` only) left over from before the backend endpoint existed — caught by the user actually clicking it. Wired to the real `POST /api/v1/leads`.
- **Testing a state-mutating action against real data.** Drove the "Reach out" button with browser automation to verify it worked, using whatever leads happened to be in the DB at the time — which turned out to be the user's own real submissions, not synthetic test data. It genuinely flipped one to `REACHED_OUT`. Caught and reverted directly in the DB. **Lesson: create disposable synthetic leads for any test that mutates state, the same way read-only checks (like the table redesign screenshot) don't need to bother.**
- **CI never applied migrations before running tests.** `.github/workflows/ci.yml`'s backend job started Postgres and waited for connectivity, but the step list went straight from "DB is reachable" to `pytest` — no `alembic upgrade head` in between. Every backend test touching `leads`/`lead_resumes` failed with `relation "..." does not exist` on GitHub Actions, which always starts from a truly empty DB. This never surfaced locally because the local `.pg0data/` had been migrated once early in the build and just kept accumulating state from then on — a fresh DB is a fundamentally different test than a long-lived one. Fixed by adding the missing step. **Lesson: "it passes locally" isn't proof the CI config is right if the local DB has never actually been fresh during the whole session — worth periodically testing against a genuinely empty DB, not just trusting the CI YAML reads correctly.**
- **Tests would have used real SMTP credentials once `backend/.env` had real ones.** `Settings` loads `.env` by default, and `get_settings()` is what both the app *and* `notify_lead_created()` in tests read from. The `test_notify_lead_created_skips_silently_when_smtp_not_configured` test relied on `smtp_username`/`smtp_password` defaulting empty — true only as long as no real `.env` existed. The moment the user filled in a real Gmail App Password for actual usage, every test that creates a lead (most of `test_leads.py`, plus the notifications test itself) would have started sending real emails through their real Gmail account on every `pytest` run — no mocking, no isolation. Caught before it happened (user asked to confirm this couldn't occur) rather than by observing a spam email land somewhere. Fixed with an autouse fixture in `conftest.py` that forces SMTP off for every test regardless of `.env`; the one test that needs "SMTP configured" behavior monkeypatches its own fake credentials *and* mocks `smtplib.SMTP` itself, so it was never at risk either way. **Lesson: any setting that gates a real side effect (sending email, charging a card, etc.) needs an explicit test-suite override, not just a "defaults to off" hope — because the default stops applying the moment real config shows up for legitimate reasons.**
- **Prospect email arrived, attorney email didn't — turned out to be spam filtering, not a code bug.** Diagnosed with a raw `smtplib` send to each address individually and inspected `send_message()`'s return value (empty dict = full acceptance for all recipients on that call): Gmail returned `250 2.0.0 OK` and an empty refused-recipients dict for *both* the plain address and the `+attorney`-tagged one — identical acceptance at the protocol level. So the send code was never the problem; a plus-addressed variant getting filtered differently by Gmail's spam heuristics than the base address is a mail-provider behavior, not something the app controls. Improved the actual email content afterward anyway (see "Rewrite the notification email content" in CHANGELOG) since plain-text-only script mail is genuinely more spam-prone regardless.
- **A diagnostic command leaked the real App Password.** While tracing the SMTP conversation above, ran `smtplib` with `set_debuglevel(1)` to see the protocol exchange with Gmail. That debug output includes the raw `AUTH PLAIN <base64>` line — base64 of `\0username\0password`, trivially reversible — and a `grep -v` filter meant to strip sensitive lines didn't match that specific line format, so the encoded real password printed directly into tool output/the session transcript. Disclosed immediately, with a recommendation to rotate the App Password. **Lesson: this is the same class of mistake as the two entries above it — "should be safe by default" isn't enough for anything that touches a real secret. Never enable raw protocol-level debug logging with real credentials in scope; redact by not generating the output at all (e.g. `set_debuglevel(0)`, or inspect return values instead of the wire conversation), not by filtering after the fact.**
- **A stale reload picked up new routes inconsistently, then a genuinely stuck OS-level socket masked the real fix.** After adding the auth router, `uvicorn --reload` kept serving a build without `/api/v1/auth/*` even after repeated restarts and confirming no old process remained (`wmic`/`tasklist` found nothing). Eventually traced to two separate things stacked on top of each other: (1) on this machine, `--reload`'s WatchFiles subprocess mechanism can serve stale routes even after a clean restart — confirmed by testing the exact same code without `--reload` on a fresh port and getting the correct routes immediately; (2) independently, port 8010 itself had a genuinely dead OS-level listening socket (`Get-NetTCPConnection` showed a `LISTENING` entry whose owning PID resolved to no real process via `Get-Process`/`tasklist`) that silently caused every new bind attempt to fail — uvicorn logged `[Errno 10048] address already in use` and exited, so `curl` was actually hitting a *previous* still-alive process this whole time, not the fresh one just started. Resolved by moving off port 8010 entirely for the rest of the session (a live process on a different port serves the code correctly) rather than continuing to chase a phenomenon that had two independent causes. **Lesson: when "I definitely restarted this and it's still wrong," verify the *new* process's PID is actually the one answering (e.g. via the process's own startup log, not just "no error was printed") before concluding the code itself is broken — and don't assume a single explanation once the first hypothesis proves incomplete.**
- **First verification of the `SEED_DEV_ADMIN` guard was a false negative — a real methodology mistake, caught before it was reported as fact.** Tested "does the seed skip when the flag is unset" by overriding only `DATABASE_URL` via a shell env var and running `alembic upgrade head` against a fresh DB — the admin account still got created. The command looked like it tested "unset," but `backend/.env` (which pydantic-settings reads unconditionally, not just for vars missing from the shell environment) already had `SEED_DEV_ADMIN=true` in it from setting up the real feature moments earlier, so the test was actually exercising the "on" path while appearing to exercise "off." Re-ran with `SEED_DEV_ADMIN` explicitly overridden in the shell (not just relying on it being absent) against a second fresh DB, which correctly showed zero attorneys created — then confirmed the positive case on a third fresh DB. **Lesson: overriding one env var via the shell doesn't isolate a test from a `.env` file that already sets a different var to the value you're trying to rule out — when testing a config toggle's "off" behavior, override that specific var explicitly rather than assuming its absence from the command line means it's unset.**

### Environment/tooling quirks (not app bugs, but cost real debugging time)

- Sending `kill -TERM` through Git Bash/MSYS to a native Windows process doesn't reliably propagate — real interactive Ctrl+C works fine; this only affected scripted testing from this session, not actual usage.
- `source .venv/Scripts/activate && cmd &` backgrounds the whole compound command as one job in Git Bash, which forks a subshell — so the `source` doesn't activate the venv for *later* commands in the same script. Splitting into `source ...` on its own line first avoids it.
- `curl -F "resume=@C:/Windows/Temp/file.pdf"` failed (exit 26, "couldn't read file") from Git Bash; using a relative path in the repo's working directory worked. Environment-specific curl/path quirk.
- The auto-generated Alembic migration file failed `ruff check` (deprecated typing style, unsorted imports) — harmless boilerplate, fixed with `ruff check --fix`.
- `HTTP_413_REQUEST_ENTITY_TOO_LARGE` is deprecated in current Starlette/FastAPI — use `HTTP_413_CONTENT_TOO_LARGE`.
- `chromium-cli` (the usual tool for screenshotting a running dev server) isn't available in this Windows/Git-Bash environment. Fallback: install `playwright` ad hoc into a scratch directory (`npm install playwright && npx playwright install chromium`) and drive it with a small one-off Node script — not a project dependency, just a verification tool.
- To verify SMTP-sending code for real without real credentials: `pip install aiosmtpd` (temporary, not a project dependency — uninstalled after) and run `python -m aiosmtpd -n -l localhost:1025` for a real local SMTP server to point the app at (`SMTP_HOST=localhost SMTP_PORT=1025 SMTP_USE_TLS=false`). Redirect its stdout to a file with `python -u` (unbuffered) or output won't flush promptly.

## Known limitations (flagged, not yet fixed)

- No per-test DB isolation/rollback fixture (see above) — real test-infra work, bigger than any single feature pass so far.
- `GET /api/v1/leads` has no pagination — fine at current scale, will need revisiting if lead volume grows.
- Resume content-type validation is client-supplied (`resume.content_type`), not magic-byte sniffed — spoofable, acceptable for now.
- **This dev machine's port 8010 is currently stuck at the OS level** (a `LISTENING` socket with no owning process — see the debugging log entry above). Backend/frontend were left running on 8012/pointed at 8012 for this session as a workaround; 8010 remains the documented project default and should work again after a reboot. `frontend/.env.local` was changed to 8012 for this session — change it back to `http://localhost:8010` once 8010 is confirmed working again.
- No self-service "forgot password" or password-change flow for attorneys — `backend/scripts/create_attorney.py` can reset a password (it upserts), but that requires shell/DB access, not something an attorney can do themselves.
